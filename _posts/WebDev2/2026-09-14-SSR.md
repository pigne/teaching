## 0. Le fil conducteur de l'année

Tout le cours de M2 tient dans une seule idée : **une donnée part d'une base et finit sous les yeux d'un utilisateur**. Entre les deux, elle traverse des frontières, et à chaque frontière on peut perdre le typage, la sécurité, ou la performance.

```
schema.prisma → types Prisma → validation (Zod) → frontière réseau
              → contrat d'API → types du client → composant → pixels
```

- **Partie 1** (ce cours) : de la base jusqu'au composant, dans une seule application.
- **Partie 2** : on coupe au milieu et on formalise le contrat (Web Services).
- **Partie 3** : on s'occupe de la dernière étape, jusqu'aux pixels (visualisation).

Gardez ce schéma en tête. À chaque nouveauté, demandez-vous : **où suis-je sur cette chaîne, et qu'est-ce que je risque d'y perdre ?**

## 1. La « Big Picture »

Une application Web moderne repose sur quelques couches :

| Couche | Rôle | Outil |
|--------|------|-------|
| **Interface** | Ce que voit l'utilisateur | React (via **Next.js**) |
| **Logique serveur** | Traitement des requêtes, rendu, mutations | **Next.js** (composants serveur, Server Actions) |
| **Données** | Stockage et accès | **Prisma** + PostgreSQL |
| **Sécurité** | Identité, sessions, permissions | **Better Auth** + logique métier |

Le tout dans **un seul projet TypeScript**.

### Flux complet d'une page « Annonces »

1. L'utilisateur visite `/annonces`.
2. Next.js exécute du code **sur le serveur** → interroge la base via Prisma.
3. Le HTML est envoyé au navigateur, déjà rempli.
4. Les parties interactives sont « hydratées » côté client.
5. Une action (publier, supprimer) repart vers le serveur via une **Server Action**.

```txt
Navigateur ──▶ Next.js (serveur) ──▶ Prisma ──▶ PostgreSQL
       ▲             │
       │             └──▶ Better Auth (session, rôles)
       │
       └──◀─── HTML + données
```

## 3. Le concept central : composants serveur et composants client

C'est **le** point qui détermine si vous comprenez Next.js ou si vous le subissez.

Dans l'App Router, **tout composant est un composant serveur par défaut**.

### Composant serveur (par défaut)

- S'exécute **sur le serveur**, jamais dans le navigateur.
- Peut être `async`, peut interroger la base directement.
- Peut lire des secrets (variables d'environnement, clés d'API).
- **Son code n'est jamais envoyé au navigateur** → bundle plus léger.
- Ne peut pas utiliser `useState`, `useEffect`, ni gérer un `onClick`.

```tsx
// src/app/annonces/page.tsx — composant serveur
import { prisma } from "@/lib/prisma"

export default async function AnnoncesPage() {
  const annonces = await prisma.annonce.findMany()   // requête SQL, côté serveur

  return (
    <ul>
      {annonces.map(a => <li key={a.id}>{a.titre} — {a.prix} €</li>)}
    </ul>
  )
}
```

Pas de `useEffect`, pas de `fetch`, pas d'état de chargement. La donnée est là avant que le HTML parte.

### Composant client (opt-in)

Il faut le déclarer explicitement avec la directive `"use client"` en tête de fichier.

- Son code **est envoyé au navigateur**.
- Peut utiliser `useState`, `useEffect`, les gestionnaires d'événements.
- **Ne peut pas** être `async`, ni accéder à la base ou aux secrets.

```tsx
// src/components/FiltrePrix.tsx
"use client"

import { useState } from "react"

export function FiltrePrix({ onChange }: { onChange: (v: number) => void }) {
  const [prix, setPrix] = useState(0)
  return (
    <input
      type="range" max={1000000} value={prix}
      onChange={e => { setPrix(+e.target.value); onChange(+e.target.value) }}
    />
  )
}
```

### La frontière

Un composant serveur peut **inclure** un composant client. L'inverse n'est pas vrai au sens naïf.

```
Serveur (par défaut)
  └── Serveur
        └── "use client"  ←── frontière
              └── tout ce qui est en dessous est client
```

**Ce qui traverse la frontière doit être sérialisable** : nombres, chaînes, tableaux, objets simples, dates. **Pas de fonctions**, pas de classes, pas d'instances Prisma exotiques.

```tsx
// ❌ Erreur classique
<ComposantClient onSave={() => prisma.annonce.create(...)} />
//                        ^ une fonction serveur passée en prop : impossible
```

### L'erreur que vous verrez

```
You're importing a component that needs `useState`.
This React hook only works in a Client Component.
```

Elle signifie : *ce fichier s'exécute sur le serveur, et tu y as mis du code client.*

Deux réponses possibles, et **le choix n'est pas neutre** :

1. Ajouter `"use client"` → simple, mais **tout ce qui est importé en dessous part dans le bundle**.
2. Isoler la partie interactive dans un petit composant client dédié, et garder le reste serveur → **la bonne réponse dans la majorité des cas**.

> 🎯 **Règle de conception.** Poussez la frontière client **le plus bas et le plus tard possible** dans l'arbre. Un bouton interactif ne doit pas faire basculer toute une page en client.

## 4. Routes et paramètres dynamiques

Chaque dossier sous `src/app` est une route. Un dossier `[id]` capture un segment variable.

### ⚠️ Les paramètres sont asynchrones

Depuis Next 15, `params` (et `searchParams`) sont des **Promises**.

```tsx
// ❌ Code que l'on trouve encore partout — et qui est faux
export default function AnnoncePage({ params }: { params: { id: string } }) {
  return <h1>Annonce n°{params.id}</h1>
}
```

**Ce code compile. `tsc` est content. `next build` passe.** Et pourtant la page affiche `Annonce n°` — vide. L'erreur est reléguée dans les logs du serveur :

```
Route "/annonces/[id]" used `params.id`. `params` is a Promise and must be
unwrapped with `await` or `React.use()` before accessing its properties.
```

La forme correcte :

```tsx
// ✅
export default async function AnnoncePage({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  return <h1>Annonce n°{id}</h1>
}
```

> 🎯 **La leçon dépasse le cas particulier.** Un build vert ne prouve pas que le code est correct. Ici le typage est fourni *par vous* dans l'annotation : si vous mentez au compilateur, il vous croit. Les tests et l'exécution réelle restent indispensables.

## 5. Streaming et Suspense

Une requête lente ne doit pas bloquer toute la page. React peut envoyer le HTML **en morceaux**, à mesure que les données arrivent.

### `loading.tsx`

Un fichier `loading.tsx` dans un dossier de route fournit automatiquement un état de chargement pour cette route :

```tsx
// src/app/annonces/loading.tsx
export default function Loading() {
  return <p>Chargement des annonces…</p>
}
```

### `<Suspense>` pour un contrôle fin

```tsx
import { Suspense } from "react"

export default function AnnoncePage() {
  return (
    <>
      <EnteteAnnonce />                       {/* rapide : part tout de suite */}

      <Suspense fallback={<p>Chargement des questions…</p>}>
        <Questions />                          {/* lent : streamé ensuite */}
      </Suspense>
    </>
  )
}
```

L'utilisateur voit l'essentiel immédiatement ; le reste se remplit. C'est une décision d'**architecture**, pas un détail cosmétique : elle dépend de ce que vous jugez prioritaire à l'écran.

### ⚠️ Deux pièges du streaming, à connaître absolument

**1. `loading.tsx` s'applique à tout le sous-arbre.**

Un `loading.tsx` dans `app/annonces/` ne concerne pas seulement `/annonces` :
il couvre aussi `/annonces/new`, `/annonces/[id]`, `/annonces/[id]/edit`…
Toutes ces routes passent en streaming, souvent sans qu'on l'ait voulu.

**2. En streaming, les codes de statut HTTP ne sont plus fiables.**

Les en-têtes HTTP partent **avant** l'exécution de votre composant. Donc
`notFound()` et `redirect()`, appelés plus tard, ne peuvent plus changer le
statut : la réponse est déjà partie en `200`. Le contenu réel (la page 404, la
redirection) arrive ensuite *dans le flux*.

Conséquence très concrète pour vos tests :

```bash
# Un agent tente d'éditer l'annonce d'un autre agent
curl -o /dev/null -w '%{http_code}' localhost:3000/annonces/42/edit
# → 200   alors que votre code appelle bien notFound() !
```

Vous croyez à une faille d'autorisation ; il n'y en a pas. **Et l'inverse est
vrai aussi : un `200` ne prouve pas qu'il n'y a pas de protection.**

> 🎯 **Règle pratique.** Préférez un `<Suspense>` local, placé autour du seul
> sous-composant qui attend des données, à un `loading.tsx` qui engage tout un
> sous-arbre. Vous gardez le streaming là où il sert, et des codes de statut
> exacts partout ailleurs.

```tsx
// ✅ Portée maîtrisée : seule la grille attend la base
export default async function AnnoncesPage({ searchParams }) {
  const q = await searchParams
  return (
    <>
      <Filtres q={q} />                              {/* immédiat */}
      <Suspense fallback={<Squelette />}>
        <Resultats q={q} />                          {/* streamé */}
      </Suspense>
    </>
  )
}
```

## 6. Persistance : Prisma

Prisma traduit un modèle déclaratif en tables SQL, et génère un client **typé**.

### Installation

```bash
npm install prisma@7 @prisma/client@7 @prisma/adapter-pg dotenv
npx prisma init --datasource-provider postgresql
```

> ⚠️ **Prisma 7 est une rupture.** Presque tous les exemples que vous
> trouverez en ligne — et tout ce qu'un assistant IA vous proposera — décrivent
> Prisma 6. Quatre changements :
>
> | | Prisma ≤ 6 | Prisma 7 |
> |---|---|---|
> | URL de connexion | `url = env(...)` dans le schéma | **`prisma.config.ts`** |
> | Générateur | `prisma-client-js` | **`prisma-client`** + `output` obligatoire |
> | Client | lit l'URL tout seul | ***driver adapter* obligatoire** |
> | `.env` | chargé automatiquement | **`import "dotenv/config"`** |

### Base de données locale

On travaille sur **PostgreSQL**, pas SQLite : c'est ce qui tourne en production, et certains comportements diffèrent (types, contraintes, transactions).

```yaml

    environment:
      # Docker Compose lit automatiquement le .env du même dossier

      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?manquant — copiez .env.example vers .env}
      POSTGRES_DB: ${POSTGRES_DB:?manquant — copiez .env.example vers .env}
```

### ⚠️ Configuration ou secret ? Deux choses différentes

C'est une confusion très fréquente, et elle produit du code incohérent.

| | Configuration | Secret |
|---|---|---|
| Exemples | `DATABASE_URL`, port, URL publique | clé de signature, clé d'API, mot de passe de prod |
| Pourquoi hors du code ? | pour **changer d'environnement** | pour **ne pas être lu** |
| Dans le dépôt ? | la *forme* oui (`.env.example`) | jamais, sous aucune forme |
| Régénéré par déploiement ? | non | **oui** |

Le mot de passe Postgres ci-dessus est de la **configuration en local** : il
protège une base jetable sur `localhost`, il n'y a rien à cacher. En
production, **la même variable devient un secret**.

D'où la règle : on ne l'écrit jamais en dur, *même quand elle paraît anodine*.
Le fichier garde la même forme d'un environnement à l'autre ; seules les
valeurs changent. Un `docker-compose.yml` avec `POSTGRES_PASSWORD: immo` écrit
en clair fonctionne en TP et devient une faille le jour où il part en
production.

> 💡 **Pourquoi les identifiants apparaissent deux fois dans `.env`** (une fois
> en `POSTGRES_*`, une fois dans `DATABASE_URL`) : ce sont **deux
> consommateurs différents**. Le conteneur veut des variables séparées pour
> *initialiser* la base ; le client Prisma veut une URL pour *s'y connecter*.
> Si vous changez le mot de passe, changez-le aux deux endroits.

Et le fichier commité, qui documente ce qui est attendu sans rien révéler :

```sh
# .env.example  — celui-ci EST dans le dépôt
POSTGRES_USER="immo"
POSTGRES_PASSWORD="immo"          # configuration locale, pas un secret
POSTGRES_DB="immo"
DATABASE_URL="postgresql://immo:immo@localhost:5432/immo"

# ⚠️ VRAI secret — à générer : openssl rand -base64 32
BETTER_AUTH_SECRET="à-générer"
```

> ⚠️ **Piège du `.gitignore` généré par Next.** Le template contient :
> ```
> .env*
> ```
> Ce motif ignore **aussi `.env.example`** — donc le fichier censé documenter
> votre configuration ne part jamais dans le dépôt, et votre binôme clone un
> projet sans savoir quelles variables renseigner. Ajoutez l'exception :
> ```
> .env*
> !.env.example
> ```
> Vérifiez-le plutôt que de le supposer : `git check-ignore -v .env.example`.

### La configuration (nouveau en Prisma 7)

```ts
// prisma.config.ts — à la racine du projet
import "dotenv/config";              // sinon DATABASE_URL reste undefined
import { defineConfig } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  migrations: { path: "prisma/migrations", seed: "tsx prisma/seed.ts" },
  datasource: { url: process.env["DATABASE_URL"] },
});
```

### Le modèle

```prisma
// prisma/schema.prisma
datasource db {
  provider = "postgresql"
  // ⚠️ plus de `url` ici : il vit dans prisma.config.ts
}

generator client {
  provider = "prisma-client"          // et non plus "prisma-client-js"
  output   = "../src/generated/prisma" // obligatoire
}

model Annonce {
  id          Int      @id @default(autoincrement())
  titre       String
  description String
  prix        Float
  statut      Statut   @default(BROUILLON)
  createdAt   DateTime @default(now())

  auteur      User     @relation(fields: [auteurId], references: [id])
  auteurId    String

  @@index([statut, createdAt])
}

enum Statut {
  BROUILLON
  PUBLIE
}
```

Notez `@@index` : dès que vous filtrerez sur `statut` et trierez sur `createdAt`, il servira. **Modéliser, c'est aussi anticiper les requêtes.**

### Le client partagé

En développement, le rechargement à chaud recrée les modules — et donc les connexions. D'où ce motif :

```ts
// src/lib/prisma.ts
// ⚠️ L'import vient du dossier généré, PAS de "@prisma/client".
import { PrismaClient } from "@/generated/prisma/client"
import { PrismaPg } from "@prisma/adapter-pg"

const globalForPrisma = globalThis as unknown as { prisma?: PrismaClient }

function createClient() {
  const connectionString = process.env.DATABASE_URL
  if (!connectionString) throw new Error("DATABASE_URL manquante")

  // Prisma 7 : c'est nous qui fournissons la connexion.
  const adapter = new PrismaPg({ connectionString })

  return new PrismaClient({ adapter, log: ["query"] })
}

export const prisma = globalForPrisma.prisma ?? createClient()

if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = prisma
```

Pensez à ajouter le dossier généré à `.gitignore`, et à le régénérer
automatiquement :

```json
{ "scripts": { "postinstall": "prisma generate" } }
```

> 💡 `log: ["query"]` affiche chaque requête SQL émise. **Gardez un œil sur ce flux** : c'est le moyen le plus simple de repérer qu'une page déclenche 300 requêtes au lieu de 2. On y revient au § 10.

## 7. La chaîne de types, en pratique

Prisma génère les types depuis le schéma. Ils se propagent gratuitement :

```tsx
const annonces = await prisma.annonce.findMany({ include: { auteur: true } })
// annonces : (Annonce & { auteur: User })[]  — inféré, sans annotation
```

### Où le typage se perd

Le client Prisma est typé, mais **ces types ne franchissent aucune frontière automatiquement** :

| Frontière | Ce qui se passe |
|---|---|
| `JSON.parse()` | renvoie `any` — toute garantie disparaît |
| Corps d'une requête HTTP | données arbitraires envoyées par le client |
| Formulaire (`FormData`) | tout est `string` ou `File` |
| Variable d'environnement | `string` ou `undefined` |

Un type TypeScript **n'existe pas à l'exécution**. Il ne protège de rien face à une donnée venue de l'extérieur.

### La réponse : valider au runtime

```ts
// src/lib/schemas.ts
import { z } from "zod"

export const AnnonceInput = z.object({
  titre:       z.string().min(3).max(120),
  description: z.string().min(10),
  prix:        z.number().positive(),
})

export type AnnonceInput = z.infer<typeof AnnonceInput>
```

`z.infer` produit le type TypeScript **à partir du schéma de validation** : une seule source de vérité, impossible de les désynchroniser.

```
schema.prisma ──▶ types Prisma ──▶ [frontière] ──▶ Zod ──▶ types validés
```

**Règle : toute donnée qui entre dans votre serveur passe par un schéma de validation.** Sans exception.

## 8. Muter les données : les Server Actions

Pour modifier des données, on écrivait autrefois une route d'API, puis un `fetch` côté client. Ce n'est plus nécessaire dans la plupart des cas.

Une **Server Action** est une fonction qui s'exécute sur le serveur, appelable directement depuis un composant.

```ts
// src/app/annonces/actions.ts
"use server"

import { revalidatePath } from "next/cache"
import { redirect } from "next/navigation"
import { prisma } from "@/lib/prisma"
import { exigerRole } from "@/lib/session"
import { AnnonceInput } from "@/lib/schemas"

export async function creerAnnonce(formData: FormData) {
  // 1 + 2. Authentification puis autorisation.
  const user = await exigerRole("AGENT", "ADMIN")

  // 3. Validation — la donnée est-elle acceptable ?
  const parsed = AnnonceInput.safeParse({
    titre:       formData.get("titre"),
    description: formData.get("description"),
    prix:        Number(formData.get("prix")),
  })
  if (!parsed.success) {
    return { erreurs: parsed.error.flatten().fieldErrors }
  }

  // 4. Écriture
  // L'auteur vient de la SESSION, jamais du formulaire.
  const annonce = await prisma.annonce.create({
    data: { ...parsed.data, auteurId: user.id },
  })

  // 5. Invalider le cache de la liste
  revalidatePath("/annonces")
  redirect(`/annonces/${annonce.id}`)
}
```

Utilisation, sans une ligne de JavaScript client :

```tsx
// src/app/annonces/new/page.tsx — composant serveur
import { creerAnnonce } from "../actions"

export default function NouvelleAnnonce() {
  return (
    <form action={creerAnnonce}>
      <input name="titre" required />
      <textarea name="description" required />
      <input name="prix" type="number" required />
      <button type="submit">Publier</button>
    </form>
  )
}
```

### ⚠️ Une Server Action est un point d'entrée public

C'est le contresens le plus dangereux du modèle. Next génère une URL pour chaque Server Action ; **n'importe qui peut l'appeler**, avec n'importe quels arguments, sans passer par votre formulaire.

Une Server Action doit donc être traitée **exactement comme un endpoint d'API** :

1. vérifier l'authentification,
2. vérifier l'autorisation,
3. valider les entrées.

Les trois, à chaque fois. Le fait que le bouton ne soit visible que pour les agents ne protège **rien** : c'est de la décoration côté client.

### Server Action ou Route Handler ?

| Besoin | Choix |
|---|---|
| Formulaire, mutation depuis votre propre interface | **Server Action** |
| Consommateur externe (mobile, autre service, script) | **Route Handler** (`src/app/api/.../route.ts`) |
| Webhook entrant | **Route Handler** |
| Contrat public, documenté, versionné | **Route Handler** → c'est l'objet de la partie 2 |

```ts
// src/app/api/annonces/route.ts — pour un consommateur externe
import { prisma } from "@/lib/prisma"

export async function GET() {
  const annonces = await prisma.annonce.findMany({ where: { statut: "PUBLIE" } })
  return Response.json(annonces)
}
```

> ❌ **Anti-patron.** N'écrivez jamais d'état en mémoire dans un module :
> ```ts
> let messages: string[] = []      // disparaît au redémarrage,
>                                  // incohérent dès qu'il y a 2 instances
> ```
> C'est tentant pour un exemple ; c'est faux dès la mise en production.

## 9. Authentification et autorisation

Deux questions distinctes, souvent confondues :

- **Authentification** : *qui es-tu ?*
- **Autorisation** : *as-tu le droit de faire ceci ?*

### Configuration (Better Auth)

```ts
// src/lib/auth.ts
import { betterAuth } from "better-auth"
import { prismaAdapter } from "better-auth/adapters/prisma"
import { prisma } from "./prisma"

export const auth = betterAuth({
  database: prismaAdapter(prisma, { provider: "postgresql" }),

  // Email + mot de passe : de première classe.
  // Le hachage (scrypt) est assuré par la bibliothèque.
  emailAndPassword: {
    enabled: true,
    minPasswordLength: 8,
  },

  user: {
    additionalFields: {
      role: {
        type: ["USER", "AGENT", "ADMIN"],
        defaultValue: "USER",
        input: false,          // ⚠️ voir ci-dessous
      },
    },
  },
})
```

Le schéma de base se génère depuis cette configuration :

```bash
npx @better-auth/cli generate     # écrit les modèles dans schema.prisma
npx prisma migrate dev            # puis on migre normalement
```

> ⚠️ La commande `generate` **réécrit** `prisma/schema.prisma`. Sauvegardez-le
> avant si vous y avez déjà mis vos modèles métier, et relisez le résultat :
> la fusion n'est pas toujours propre.

Et le handler, seule Route Handler imposée — elle est appelée par la
bibliothèque, pas par vos formulaires :

```ts
// src/app/api/auth/[...all]/route.ts
import { toNextJsHandler } from "better-auth/next-js"
import { auth } from "@/lib/auth"

export const { GET, POST } = toNextJsHandler(auth)
```

Lire la session côté serveur :

```ts
import { headers } from "next/headers"
import { auth } from "@/lib/auth"

// ⚠️ `headers()` est asynchrone depuis Next 15 — même logique que `params`.
const session = await auth.api.getSession({ headers: await headers() })
```

### `input: false` — le rôle appartient au serveur

C'est le détail le plus important de cette configuration.

```ts
role: { type: ["USER","AGENT","ADMIN"], defaultValue: "USER", input: false }
```

`input: false` signifie que **l'API refuse ce champ en entrée**. Un client qui
poste `role=ADMIN` à l'inscription obtient un compte `USER`, sans erreur et
sans effet.

```bash
curl -X POST /api/auth/sign-up/email \
  -d '{"email":"x@y.fr","name":"X","password":"motdepasse","role":"ADMIN"}'
# → compte créé avec role = USER
```

La différence avec un simple avertissement dans la documentation est de nature :
ici, **l'escalade de privilèges est impossible par construction**. Les rôles
sont attribués ailleurs — par un script d'initialisation, ou par une action
d'administrateur.

> 🎯 **Principe général.** Toute donnée qui détermine des droits ne doit jamais
> venir du client. Le rôle, l'identifiant de l'auteur, le montant à payer : ils
> viennent de la session ou du serveur. On y revient au § 8 (`auteurId` pris
> dans la session, jamais dans le formulaire).

### Où vit la session ? Un choix, pas une fatalité

Better Auth stocke les sessions **en base** par défaut : la table `session` est
peuplée, et un identifiant opaque circule dans un cookie. L'alternative est le
JWT, où la session *est* le cookie.

| | en base (défaut) | JWT |
|---|---|---|
| Contenu du cookie | un identifiant opaque | la session elle-même, signée |
| Révocation immédiate | ✅ supprimer la ligne | ❌ il faut attendre l'expiration |
| Requête DB par appel | oui | non |
| Passage à l'échelle | dépend de la base | sans état, très bon |

**Le bon réflexe est de savoir pourquoi vous avez choisi l'un ou l'autre.**
Pour une application qui doit pouvoir bannir un compte sur le champ, les
sessions en base sont plus sûres. Pour une API sans état répartie sur plusieurs
régions, le JWT s'impose. C'est un arbitrage, et il se justifie à l'oral.

> 💡 Vérifiez-le vous-même : connectez-vous, puis
> ```sql
> SELECT "userId", "expiresAt" FROM "session";
> ```
> La ligne est là. (Attention : la table s'appelle `session` en minuscules —
> Better Auth utilise un `@@map`.)

### Autorisation : le vrai sujet

L'authentification est un problème résolu par une bibliothèque. **L'autorisation est votre logique métier, et personne ne l'écrira à votre place.**

```ts
// ❌ Faille : IDOR (Insecure Direct Object Reference)
export async function supprimerAnnonce(id: number) {
  await prisma.annonce.delete({ where: { id } })
}
```

L'utilisateur est authentifié — donc tout va bien ? Non : **il supprime l'annonce de quelqu'un d'autre** en changeant l'identifiant.

```ts
// ✅ La propriété fait partie de la condition
export async function supprimerAnnonce(id: number) {
  const user = await exigerUtilisateur()          // lève si anonyme

  const res = await prisma.annonce.deleteMany({
    where: {
      id,
      ...(user.role === "ADMIN" ? {} : { auteurId: user.id }),
    },
  })
  if (res.count === 0) throw new Error("Introuvable ou interdit")
}
```

> 💡 **Isolez cette règle dans une fonction pure.** Si votre politique
> d'autorisation importe la bibliothèque d'authentification, vous ne pourrez
> pas la tester sans monter un serveur. Séparez :
> `authz.ts` (la règle, sans dépendance) et `session.ts` (la lecture de la
> session). C'est une contrainte de testabilité qui améliore la conception.

> 🎯 **L'IDOR est la faille la plus fréquente des applications générées automatiquement.** Un assistant IA produit volontiers le premier extrait : il est plus court, il « marche », et les tests passent tant qu'on ne teste qu'avec un seul utilisateur. **Testez toujours avec deux comptes distincts.**

### Protéger les routes

La vérification doit avoir lieu **là où la donnée est touchée** — dans le composant serveur ou la Server Action. Un middleware est un filtre de confort, pas une garantie.

```tsx
// src/app/annonces/new/page.tsx
import { redirect } from "next/navigation"
import { utilisateurCourant } from "@/lib/session"

export default async function Page() {
  const user = await utilisateurCourant()
  if (!user) redirect("/login")
  if (user.role === "USER") redirect("/interdit")
  return <FormulaireAnnonce />
}
```

## 10. Performance : la question des N+1

Regardez les logs SQL en affichant une liste d'annonces avec leur auteur :

```ts
const annonces = await prisma.annonce.findMany()
for (const a of annonces) {
  const auteur = await prisma.user.findUnique({ where: { id: a.auteurId } })
}
```

20 annonces → **21 requêtes**. C'est le *problème N+1*. Il est invisible avec 3 lignes de test et catastrophique avec 10 000.

```ts
// ✅ Nombre de requêtes constant
const annonces = await prisma.annonce.findMany({ include: { auteur: true } })
```

### Ce que fait réellement `include`

Contrairement à une idée répandue, `include` ne produit **pas** une seule
requête avec `JOIN`. Prisma émet **une requête par relation**, groupée par
`IN` :

```sql
1. SELECT COUNT(*) FROM "Annonce" WHERE statut = 'PUBLIE'
2. SELECT ... FROM "Annonce" WHERE statut = 'PUBLIE' ORDER BY ... LIMIT 6
3. SELECT ... FROM "Photo" WHERE "annonceId" IN ($1, $2, …)
4. SELECT id, name FROM "User" WHERE id IN ($1, $2, …)
```

Soit `2 + nombre de relations incluses` = 4 requêtes ici.

**Et c'est très bien** — parce que ce total **ne dépend pas du nombre de
lignes affichées**. 6 annonces ou 600 : toujours 4 requêtes.

> 🎯 **Le bon critère n'est donc pas un nombre absolu, c'est l'invariance.**
> Un N+1 se définit par un nombre de requêtes qui **croît** avec le volume.
> Pour le détecter : mesurez deux fois, avec peu puis beaucoup de lignes, et
> comparez. Si le compte bouge, vous avez un N+1.

> 🎯 **Question d'oral quasi certaine : « combien de requêtes SQL pour afficher cette page ? »**
> Ouvrez les logs et comptez. Si vous ne savez pas répondre, vous ne connaissez pas votre application.
