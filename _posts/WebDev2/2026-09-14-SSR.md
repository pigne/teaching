## Master 2 – Développement Web (Partie 1)
### Une application Web complète : composants serveur, ORM, mutations, authentification

---

## Objectifs

- Comprendre la frontière serveur / client dans une application React moderne.
- Savoir où s'exécute chaque ligne de code écrite, et pourquoi cela compte.
- Modéliser et persister des données avec un ORM typé.
- Muter des données avec les Server Actions, et savoir quand une API est
  préférable.
- Distinguer authentification et autorisation, et implémenter les deux.
- Suivre la chaîne de types de la base jusqu'à l'interface.

---

## 0. Le fil conducteur de l'année

Une donnée part d'une base et finit sous les yeux d'un utilisateur. Entre les
deux elle traverse des frontières, et à chaque frontière on peut perdre le
typage, la sécurité ou la performance.

```
schema.prisma → types Prisma → validation (Zod) → frontière réseau
              → contrat d'API → types du client → composant → pixels
```

- **Partie 1** : de la base au composant, dans une seule application.
- **Partie 2** : on coupe au milieu et on formalise le contrat.
- **Partie 3** : la dernière étape, jusqu'aux pixels.

À chaque nouveauté, situez-vous sur cette chaîne et demandez-vous ce que vous
risquez d'y perdre.

---

## 1. La « Big Picture »

| Couche | Rôle | Outil |
|--------|------|-------|
| Interface | ce que voit l'utilisateur | React, via **Next.js** |
| Logique serveur | requêtes, rendu, mutations | **Next.js** (composants serveur, Server Actions) |
| Données | stockage et accès | **Prisma** + PostgreSQL |
| Sécurité | identité, sessions, permissions | **Better Auth** + logique métier |

Le tout dans un seul projet TypeScript.

Flux d'une page « Annonces » : l'utilisateur visite `/annonces`, Next.js exécute
du code **sur le serveur** qui interroge la base via Prisma, le HTML part déjà
rempli, les parties interactives sont hydratées côté client, et une action
(publier, supprimer) repart vers le serveur via une Server Action.

```txt
Navigateur ──▶ Next.js (serveur) ──▶ Prisma ──▶ PostgreSQL
       ▲             │
       │             └──▶ Better Auth (session, rôles)
       │
       └──◀─── HTML + données
```

## 3. Composants serveur et composants client

C'est le point qui détermine si vous comprenez Next.js ou si vous le subissez.
Dans l'App Router, **tout composant est un composant serveur par défaut**.

### Composant serveur

- S'exécute sur le serveur, jamais dans le navigateur.
- Peut être `async`, peut interroger la base directement.
- Peut lire des secrets.
- Son code n'est jamais envoyé au navigateur.
- Ne peut pas utiliser `useState`, `useEffect`, ni gérer un `onClick`.

```tsx
// src/app/annonces/page.tsx
import { prisma } from "@/lib/prisma"

export default async function AnnoncesPage() {
  const annonces = await prisma.annonce.findMany()

  return (
    <ul>
      {annonces.map(a => <li key={a.id}>{a.titre} — {a.prix} €</li>)}
    </ul>
  )
}
```

Pas de `useEffect`, pas de `fetch`, pas d'état de chargement : la donnée est là
avant que le HTML parte.

### Composant client

Déclaré explicitement par la directive `"use client"` en tête de fichier. Son
code est envoyé au navigateur, il peut utiliser les hooks et les gestionnaires
d'événements, mais il ne peut pas être `async` ni accéder à la base ou aux
secrets.

```tsx
// src/components/FiltrePrix.tsx
"use client"

import { useState } from "react"

export function FiltrePrix({ onChange }: { onChange: (v: number) => void }) {
  const [prix, setPrix] = useState(0)
  return (
    <input
      type="range" max={1000000} value={prix}
      onChange={e => { setPrix(+e.target.value); onChange(+e.target.value) }}
    />
  )
}
```

### La frontière

Un composant serveur peut inclure un composant client ; l'inverse n'est pas
vrai au sens naïf.

```
Serveur (par défaut)
  └── Serveur
        └── "use client"  ←── frontière
              └── tout ce qui est en dessous est client
```

Ce qui traverse la frontière doit être **sérialisable** : nombres, chaînes,
tableaux, objets simples, dates. Pas de fonctions, pas de classes.

```tsx
// Erreur classique
<ComposantClient onSave={() => prisma.annonce.create(...)} />
//                        ^ une fonction serveur passée en prop : impossible
```

### L'erreur que vous verrez

```
You're importing a component that needs `useState`.
This React hook only works in a Client Component.
```

Elle signifie : ce fichier s'exécute sur le serveur, et vous y avez mis du code
client. Deux réponses possibles, et le choix n'est pas neutre :

1. ajouter `"use client"` — simple, mais tout ce qui est importé en dessous part
   dans le bundle ;
2. isoler la partie interactive dans un petit composant client dédié et garder
   le reste serveur — la bonne réponse dans la majorité des cas.

Règle de conception : poussez la frontière client le plus bas et le plus tard
possible dans l'arbre. Un bouton interactif ne doit pas faire basculer toute une
page en client.

## 4. Routes et paramètres dynamiques

Chaque dossier sous `src/app` est une route ; un dossier `[id]` capture un
segment variable.

Depuis Next 15, `params` et `searchParams` sont des **Promises**.

```tsx
// Code que l'on trouve encore partout, et qui est faux
export default function AnnoncePage({ params }: { params: { id: string } }) {
  return <h1>Annonce n°{params.id}</h1>
}
```

Ce code compile, `tsc` est content, `next build` passe. Et la page affiche
`Annonce n°` — vide. L'erreur est reléguée dans les logs du serveur :

```
Route "/annonces/[id]" used `params.id`. `params` is a Promise and must be
unwrapped with `await` or `React.use()` before accessing its properties.
```

La forme correcte :

```tsx
export default async function AnnoncePage({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  return <h1>Annonce n°{id}</h1>
}
```

La portée dépasse le cas particulier : le type vient de l'annotation que vous
fournissez vous-même. Si elle est fausse, le compilateur vous croit. Un build
vert ne prouve donc pas la correction du code.

## 5. Streaming et Suspense

Une requête lente ne doit pas bloquer toute la page. React peut envoyer le HTML
en morceaux, à mesure que les données arrivent.

Un fichier `loading.tsx` dans un dossier de route fournit automatiquement un
état de chargement pour cette route :

```tsx
// src/app/annonces/loading.tsx
export default function Loading() {
  return <p>Chargement des annonces…</p>
}
```

`<Suspense>` donne un contrôle plus fin :

```tsx
import { Suspense } from "react"

export default function AnnoncePage() {
  return (
    <>
      <EnteteAnnonce />                       {/* rapide : part tout de suite */}

      <Suspense fallback={<p>Chargement des questions…</p>}>
        <Questions />                          {/* lent : streamé ensuite */}
      </Suspense>
    </>
  )
}
```

L'utilisateur voit l'essentiel immédiatement, le reste se remplit. C'est une
décision d'architecture : elle dépend de ce que vous jugez prioritaire à
l'écran.

### Deux pièges

**`loading.tsx` s'applique à tout le sous-arbre.** Un `loading.tsx` dans
`app/annonces/` ne concerne pas seulement `/annonces` : il couvre aussi
`/annonces/new`, `/annonces/[id]`, `/annonces/[id]/edit`. Toutes ces routes
passent en streaming, souvent sans qu'on l'ait voulu.

**En streaming, les codes de statut HTTP ne sont plus fiables.** Les en-têtes
partent *avant* l'exécution de votre composant : `notFound()` et `redirect()`,
appelés plus tard, ne peuvent plus changer le statut. La réponse est déjà partie
en `200`, et le contenu réel arrive ensuite dans le flux.

```bash
# Un agent tente d'éditer l'annonce d'un autre agent
curl -o /dev/null -w '%{http_code}' localhost:3000/annonces/42/edit
# → 200   alors que le code appelle bien notFound()
```

Vous croyez à une faille d'autorisation ; il n'y en a pas. Et l'inverse est vrai
aussi : un `200` ne prouve pas l'absence de protection.

Préférez donc un `<Suspense>` local, placé autour du seul sous-composant qui
attend des données, à un `loading.tsx` qui engage tout un sous-arbre. Vous
gardez le streaming là où il sert, et des codes de statut exacts ailleurs.

```tsx
export default async function AnnoncesPage({ searchParams }) {
  const q = await searchParams
  return (
    <>
      <Filtres q={q} />                              {/* immédiat */}
      <Suspense fallback={<Squelette />}>
        <Resultats q={q} />                          {/* streamé */}
      </Suspense>
    </>
  )
}
```

## 6. Persistance : Prisma

```bash
npm install prisma@7 @prisma/client@7 @prisma/adapter-pg dotenv
npx prisma init --datasource-provider postgresql
```

Prisma 7 est une rupture. Presque tous les exemples en ligne — et tout ce qu'un
assistant proposera — décrivent Prisma 6.

| | Prisma ≤ 6 | Prisma 7 |
|---|---|---|
| URL de connexion | `url = env(...)` dans le schéma | **`prisma.config.ts`** |
| Générateur | `prisma-client-js` | **`prisma-client`** + `output` obligatoire |
| Client | lit l'URL seul | ***driver adapter* obligatoire** |
| `.env` | chargé automatiquement | **`import "dotenv/config"`** |

Le code généré n'est plus écrit dans `node_modules` mais dans votre projet, à
l'emplacement que vous indiquez — d'où l'`output` obligatoire. C'est du
TypeScript ordinaire, compilé avec le reste de votre code, et que vous pouvez
ouvrir et lire.

### Base de données locale

On travaille sur PostgreSQL, pas SQLite : c'est ce qui tourne en production, et
certains comportements diffèrent.

```yaml
# docker-compose.yml — aucun identifiant écrit ici
services:
  db:
    image: postgres:17
    environment:
      # Compose lit le .env du même dossier et substitue les ${...}.
      # La forme ${VAR:?message} fait ÉCHOUER la commande si la variable manque.
      POSTGRES_USER: ${POSTGRES_USER:?manquant — copiez .env.example vers .env}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?manquant — copiez .env.example vers .env}
      POSTGRES_DB: ${POSTGRES_DB:?manquant — copiez .env.example vers .env}
    ports: ["${POSTGRES_PORT:-5432}:5432"]
    volumes: ["pgdata:/var/lib/postgresql/data"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $$POSTGRES_USER -d $$POSTGRES_DB"]
      interval: 5s
      retries: 10
volumes:
  pgdata:
```

```sh
# .env   (ignoré par git — c'est .env.example qui est commité)
POSTGRES_USER="immo"
POSTGRES_PASSWORD="immo"
POSTGRES_DB="immo"
POSTGRES_PORT="5432"

DATABASE_URL="postgresql://immo:immo@localhost:5432/immo"
```

```bash
docker compose up -d
```

### Configuration ou secret

| | Configuration | Secret |
|---|---|---|
| Exemples | `DATABASE_URL`, port, URL publique | clé de signature, clé d'API |
| Pourquoi hors du code | pour **changer d'environnement** | pour **ne pas être lu** |
| Dans le dépôt | la *forme* (`.env.example`) | jamais |
| Régénéré par déploiement | non | **oui** |

Le mot de passe Postgres ci-dessus est de la configuration locale : il protège
une base jetable sur `localhost`. En production, la même variable devient un
secret. D'où la règle de ne jamais l'écrire en dur, même quand elle paraît
anodine : le fichier garde la même forme d'un environnement à l'autre, seules
les valeurs changent.

Les identifiants apparaissent deux fois dans `.env` — en `POSTGRES_*` puis dans
`DATABASE_URL` — parce que ce sont deux consommateurs différents : le conteneur
veut des variables séparées pour *initialiser* la base, le client Prisma veut
une URL pour *s'y connecter*.

```sh
# .env.example  — celui-ci EST dans le dépôt
POSTGRES_USER="immo"
POSTGRES_PASSWORD="immo"          # configuration locale, pas un secret
POSTGRES_DB="immo"
DATABASE_URL="postgresql://immo:immo@localhost:5432/immo"

# VRAI secret — à générer : openssl rand -base64 32
BETTER_AUTH_SECRET="à-générer"
```

> ⚠️ Le `.gitignore` de `create-next-app` contient `.env*`, qui ignore **aussi
> `.env.example`**. Le fichier censé documenter votre configuration ne part
> alors jamais dans le dépôt, et votre binôme clone un projet sans savoir
> quelles variables renseigner. Ajoutez `!.env.example`, et vérifiez-le :
> `git check-ignore -v .env.example`.

### La configuration Prisma 7

```ts
// prisma.config.ts — à la racine du projet
import "dotenv/config";              // sinon DATABASE_URL reste undefined
import { defineConfig } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  migrations: { path: "prisma/migrations", seed: "tsx prisma/seed.ts" },
  datasource: { url: process.env["DATABASE_URL"] },
});
```

### Le modèle

```prisma
// prisma/schema.prisma
datasource db {
  provider = "postgresql"
  // plus de `url` ici : il vit dans prisma.config.ts
}

generator client {
  provider = "prisma-client"           // et non plus "prisma-client-js"
  output   = "../src/generated/prisma" // obligatoire
}

model Annonce {
  id          Int      @id @default(autoincrement())
  titre       String
  description String
  prix        Float
  statut      Statut   @default(BROUILLON)
  createdAt   DateTime @default(now())

  auteur      User     @relation(fields: [auteurId], references: [id])
  auteurId    String

  @@index([statut, createdAt])
}

enum Statut {
  BROUILLON
  PUBLIE
}
```

L'`@@index` servira dès que vous filtrerez sur `statut` et trierez sur
`createdAt` : modéliser, c'est aussi anticiper les requêtes.

```bash
npx prisma migrate dev --name init
npx prisma studio          # exploration graphique
```

### Le client partagé

```ts
// src/lib/prisma.ts
// L'import vient du dossier généré, PAS de "@prisma/client".
import { PrismaClient } from "@/generated/prisma/client"
import { PrismaPg } from "@prisma/adapter-pg"

const globalForPrisma = globalThis as unknown as { prisma?: PrismaClient }

function createClient() {
  const connectionString = process.env.DATABASE_URL
  if (!connectionString) throw new Error("DATABASE_URL manquante")

  return new PrismaClient({
    adapter: new PrismaPg({ connectionString }),
    log: ["query"],
  })
}

export const prisma = globalForPrisma.prisma ?? createClient()

if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = prisma
```

Le motif `globalThis` évite d'ouvrir un pool de connexions à chaque
rechargement à chaud. Le dossier généré est un artefact de build : ajoutez-le à
`.gitignore` et régénérez-le automatiquement.

```json
{ "scripts": { "postinstall": "prisma generate" } }
```

`log: ["query"]` affiche chaque requête SQL émise : c'est le moyen le plus
simple de repérer qu'une page en déclenche 300 au lieu de 2 (§ 10).

## 7. La chaîne de types

Prisma génère les types depuis le schéma, et ils se propagent gratuitement.

```tsx
const annonces = await prisma.annonce.findMany({ include: { auteur: true } })
// annonces : (Annonce & { auteur: User })[]  — inféré, sans annotation
```

Mais ces types ne franchissent **aucune frontière** automatiquement.

| Frontière | Ce qui se passe |
|---|---|
| `JSON.parse()` | renvoie `any` |
| Corps d'une requête HTTP | données arbitraires envoyées par le client |
| Formulaire (`FormData`) | tout est `string` ou `File` |
| Variable d'environnement | `string` ou `undefined` |

Un type TypeScript n'existe pas à l'exécution : il ne protège de rien face à
une donnée venue de l'extérieur.

```ts
// src/lib/schemas.ts
import { z } from "zod"

export const AnnonceInput = z.object({
  titre:       z.string().min(3).max(120),
  description: z.string().min(10),
  prix:        z.number().positive(),
})

export type AnnonceInput = z.infer<typeof AnnonceInput>
```

`z.infer` produit le type TypeScript **à partir du schéma de validation** : une
seule source de vérité, impossible de les désynchroniser.

```
schema.prisma ──▶ types Prisma ──▶ [frontière] ──▶ Zod ──▶ types validés
```

Règle : toute donnée qui entre dans votre serveur passe par un schéma de
validation, sans exception.

## 8. Muter les données : les Server Actions

Une Server Action est une fonction qui s'exécute sur le serveur, appelable
directement depuis un composant. Écrire une route d'API puis un `fetch` client
n'est plus nécessaire dans la plupart des cas.

```ts
// src/app/annonces/actions.ts
"use server"

import { revalidatePath } from "next/cache"
import { redirect } from "next/navigation"
import { prisma } from "@/lib/prisma"
import { exigerRole } from "@/lib/session"
import { AnnonceInput } from "@/lib/schemas"

export async function creerAnnonce(formData: FormData) {
  // 1 + 2. Authentification puis autorisation.
  const user = await exigerRole("AGENT", "ADMIN")

  // 3. Validation.
  const parsed = AnnonceInput.safeParse({
    titre:       formData.get("titre"),
    description: formData.get("description"),
    prix:        Number(formData.get("prix")),
  })
  if (!parsed.success) {
    return { erreurs: parsed.error.flatten().fieldErrors }
  }

  // 4. Écriture — l'auteur vient de la SESSION, jamais du formulaire.
  const annonce = await prisma.annonce.create({
    data: { ...parsed.data, auteurId: user.id },
  })

  // 5. Invalidation du cache.
  revalidatePath("/annonces")
  redirect(`/annonces/${annonce.id}`)
}
```

Utilisation, sans une ligne de JavaScript client :

```tsx
// src/app/annonces/new/page.tsx
import { creerAnnonce } from "../actions"

export default function NouvelleAnnonce() {
  return (
    <form action={creerAnnonce}>
      <input name="titre" required />
      <textarea name="description" required />
      <input name="prix" type="number" required />
      <button type="submit">Publier</button>
    </form>
  )
}
```

### Une Server Action est un point d'entrée public

Next génère une URL pour chaque Server Action : n'importe qui peut l'appeler,
avec n'importe quels arguments, sans passer par votre formulaire.

Une Server Action doit donc être traitée exactement comme un endpoint d'API :
vérifier l'authentification, vérifier l'autorisation, valider les entrées. Les
trois, à chaque fois. Le fait que le bouton ne soit visible que pour les agents
ne protège rien — c'est de la décoration côté client.

### Server Action ou Route Handler

| Besoin | Choix |
|---|---|
| Formulaire, mutation depuis votre propre interface | **Server Action** |
| Consommateur externe (mobile, autre service, script) | **Route Handler** |
| Webhook entrant | **Route Handler** |
| Contrat public, documenté, versionné | **Route Handler** → objet de la partie 2 |

```ts
// src/app/api/annonces/route.ts — pour un consommateur externe
import { prisma } from "@/lib/prisma"

export async function GET() {
  const annonces = await prisma.annonce.findMany({ where: { statut: "PUBLIE" } })
  return Response.json(annonces)
}
```

N'écrivez jamais d'état en mémoire dans un module : il disparaît au redémarrage
et devient incohérent dès qu'il y a deux instances.

```ts
let messages: string[] = []      // tentant pour un exemple, faux en production
```

## 9. Authentification et autorisation

Deux questions distinctes, souvent confondues : l'authentification répond
« qui es-tu ? », l'autorisation répond « as-tu le droit de faire ceci ? ».

### Configuration

```ts
// src/lib/auth.ts
import { betterAuth } from "better-auth"
import { prismaAdapter } from "better-auth/adapters/prisma"
import { prisma } from "./prisma"

export const auth = betterAuth({
  database: prismaAdapter(prisma, { provider: "postgresql" }),

  emailAndPassword: {
    enabled: true,
    minPasswordLength: 8,
  },

  user: {
    additionalFields: {
      role: {
        type: ["USER", "AGENT", "ADMIN"],
        defaultValue: "USER",
        input: false,
      },
    },
  },
})
```

Le hachage des mots de passe est assuré par la bibliothèque (scrypt). Le schéma
de base se génère depuis cette configuration :

```bash
npx @better-auth/cli generate     # écrit les modèles dans schema.prisma
npx prisma migrate dev
```

La commande `generate` **réécrit** `prisma/schema.prisma`. Sauvegardez-le avant
si vous y avez déjà mis vos modèles métier, et relisez le résultat : la fusion
n'est pas toujours propre.

```ts
// src/app/api/auth/[...all]/route.ts
import { toNextJsHandler } from "better-auth/next-js"
import { auth } from "@/lib/auth"

export const { GET, POST } = toNextJsHandler(auth)
```

Lire la session côté serveur — `headers()` est asynchrone depuis Next 15, même
logique que `params` :

```ts
import { headers } from "next/headers"
import { auth } from "@/lib/auth"

const session = await auth.api.getSession({ headers: await headers() })
```

### `input: false` — le rôle appartient au serveur

```ts
role: { type: ["USER","AGENT","ADMIN"], defaultValue: "USER", input: false }
```

`input: false` signifie que l'API refuse ce champ en entrée. Un client qui poste
`role=ADMIN` à l'inscription obtient un compte `USER`, sans erreur et sans
effet.

```bash
curl -X POST /api/auth/sign-up/email \
  -d '{"email":"x@y.fr","name":"X","password":"motdepasse","role":"ADMIN"}'
# → compte créé avec role = USER
```

La différence avec un simple avertissement dans la documentation est de nature :
l'escalade de privilèges devient impossible par construction. Les rôles sont
attribués ailleurs — par un script d'initialisation ou une action
d'administrateur.

Principe général : toute donnée qui détermine des droits ne vient jamais du
client. Le rôle, l'identifiant de l'auteur, le montant à payer viennent de la
session ou du serveur.

### Où vit la session

Better Auth stocke les sessions **en base** par défaut : la table `session` est
peuplée, et un identifiant opaque circule dans un cookie. L'alternative est le
JWT, où la session *est* le cookie.

| | en base (défaut) | JWT |
|---|---|---|
| Contenu du cookie | un identifiant opaque | la session elle-même, signée |
| Révocation immédiate | supprimer la ligne | impossible avant expiration |
| Requête DB par appel | oui | non |
| Passage à l'échelle | dépend de la base | sans état, très bon |

Pour une application qui doit pouvoir bannir un compte sur le champ, les
sessions en base sont plus sûres ; pour une API sans état répartie sur plusieurs
régions, le JWT s'impose. C'est un arbitrage, et il se justifie à l'oral.
Vérifiez-le : après connexion, `SELECT "userId", "expiresAt" FROM "session";`
— la ligne est là. La table s'appelle `session` en minuscules, Better Auth
utilise un `@@map`.

### Autorisation

L'authentification est un problème résolu par une bibliothèque. L'autorisation
est votre logique métier, et personne ne l'écrira à votre place.

```ts
// Faille : IDOR (Insecure Direct Object Reference)
export async function supprimerAnnonce(id: number) {
  await prisma.annonce.delete({ where: { id } })
}
```

L'utilisateur est authentifié, donc tout va bien ? Non : il supprime l'annonce
de quelqu'un d'autre en changeant l'identifiant.

```ts
// La propriété fait partie de la condition
export async function supprimerAnnonce(id: number) {
  const user = await exigerUtilisateur()

  const res = await prisma.annonce.deleteMany({
    where: {
      id,
      ...(user.role === "ADMIN" ? {} : { auteurId: user.id }),
    },
  })
  if (res.count === 0) throw new Error("Introuvable ou interdit")
}
```

Isolez cette règle dans une fonction **pure**. Si votre politique
d'autorisation importe la bibliothèque d'authentification, vous ne pourrez pas
la tester sans monter un serveur. Séparez `authz.ts` (la règle, sans
dépendance) et `session.ts` (la lecture de la session) : c'est une contrainte de
testabilité qui améliore la conception.

L'IDOR est la faille la plus fréquente des applications générées
automatiquement : le premier extrait est plus court, il « marche », et les tests
passent tant qu'on ne teste qu'avec un seul utilisateur. Testez toujours avec
deux comptes distincts.

### Protéger les routes

La vérification doit avoir lieu là où la donnée est touchée — dans le composant
serveur ou la Server Action. Un middleware est un filtre de confort, pas une
garantie.

```tsx
// src/app/annonces/new/page.tsx
import { redirect } from "next/navigation"
import { utilisateurCourant } from "@/lib/session"

export default async function Page() {
  const user = await utilisateurCourant()
  if (!user) redirect("/login")
  if (user.role === "USER") redirect("/interdit")
  return <FormulaireAnnonce />
}
```

## 10. Performance : les N+1

```ts
const annonces = await prisma.annonce.findMany()
for (const a of annonces) {
  const auteur = await prisma.user.findUnique({ where: { id: a.auteurId } })
}
```

20 annonces donnent 21 requêtes. C'est le *problème N+1* : invisible avec trois
lignes de test, catastrophique avec dix mille.

```ts
const annonces = await prisma.annonce.findMany({ include: { auteur: true } })
```

### Ce que fait réellement `include`

Contrairement à une idée répandue, `include` ne produit pas une seule requête
avec `JOIN`. Prisma émet **une requête par relation**, groupée par `IN` :

```sql
1. SELECT COUNT(*) FROM "Annonce" WHERE statut = 'PUBLIE'
2. SELECT ... FROM "Annonce" WHERE statut = 'PUBLIE' ORDER BY ... LIMIT 6
3. SELECT ... FROM "Photo" WHERE "annonceId" IN ($1, $2, …)
4. SELECT id, name FROM "User" WHERE id IN ($1, $2, …)
```

Soit `2 + nombre de relations incluses` = 4 requêtes ici. Et c'est très bien,
parce que ce total **ne dépend pas du nombre de lignes affichées** : 6 annonces
ou 600, toujours 4 requêtes.

Le bon critère n'est donc pas un nombre absolu mais l'**invariance**. Un N+1 se
définit par un nombre de requêtes qui *croît* avec le volume : mesurez deux
fois, avec peu puis beaucoup de lignes, et comparez.

Question d'oral quasi certaine : « combien de requêtes SQL pour afficher cette
page ? » Ouvrez les logs et comptez.
