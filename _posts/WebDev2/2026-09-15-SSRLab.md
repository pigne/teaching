## Application Web de gestion d'annonces immobilières

Ce TP met en œuvre une application Web **full-stack** complète avec l'écosystème TypeScript : composants serveur, ORM, mutations, authentification et autorisation.

Il sert de base aux deux TP suivants (**Web Services**, puis **Visualisation**). Soignez-le : vous allez vivre avec.

---

## ⚠️ Avertissement préalable : comment ce TP est évalué

Le code d'une application de ce type est aujourd'hui largement générable automatiquement. **Nous ne l'ignorons pas, et l'usage d'assistants IA est autorisé.**

En conséquence, l'évaluation ne porte pas sur la production du code, mais sur trois choses que personne ne peut produire à votre place :

1. **des cibles mesurées** (§ Critères mesurables) — vérifiées automatiquement ;
2. **votre compréhension**, à l'oral, machine ouverte, sur *votre* code ;
3. **votre jugement critique**, tracé dans un fichier `AI.md`.

Un projet entièrement généré et non compris se repère en deux questions. Vous êtes prévenus.

## User Story

Un site de gestion d'annonces immobilières permet de **publier, consulter et gérer** des annonces selon les rôles.

### Rôles et droits

- **Visiteur (non connecté)**
  - Consulte les annonces **publiées** uniquement.
- **Utilisateur connecté (`USER`)**
  - Pose des questions sur une annonce.
  - Enregistre des annonces en favoris.
- **Agent immobilier (`AGENT`)**
  - Crée, modifie, supprime **ses propres** annonces.
  - Répond aux questions posées sur ses annonces.
  - Publie ou dépublie ses annonces.
- **Administrateur (`ADMIN`)**
  - Tous les droits.

### Contenu d'une annonce

- titre, description détaillée
- type de bien (*vente* / *location*)
- statut de publication (*brouillon* / *publiée*)
- statut du bien (*disponible* / *loué* / *vendu*)
- prix, date de disponibilité
- liste de photos (upload ou glisser-déposer)
- questions / réponses associées

---

## Objectifs pédagogiques

- **Modéliser** des données et anticiper les requêtes (relations, index).
- **Placer consciemment la frontière serveur / client** et savoir la justifier.
- **Muter** des données avec les Server Actions, en les sécurisant correctement.
- **Distinguer authentification et autorisation**, et implémenter les deux.
- **Valider** toute donnée entrante au runtime.
- **Mesurer** le comportement de son application plutôt que le supposer.

## Contraintes techniques

### Socle imposé

| Élément | Contrainte |
|---|---|
| Framework | Next.js 16+, **App Router** |
| Langage | TypeScript, `strict: true` |
| Base | **PostgreSQL via Docker** — SQLite refusé |
| ORM | **Prisma 7.x** — ne passez pas en 8, elle casse Better Auth |
| Auth | **Better Auth** |
| Validation | Zod, sur **toute** entrée |
| Tests | Vitest, sur une **base de test séparée** |

### Installation

Utilisez ces commandes telles quelles. Les versions sont épinglées pour de
bonnes raisons (voir § 2 du cours) :

```bash
npx create-next-app@16 immobilier-app --typescript --tailwind --app --src-dir --eslint
cd immobilier-app

npm install prisma@7 @prisma/client@7 @prisma/adapter-pg dotenv
npm install better-auth zod
npm install -D vitest @types/node@^26 tsx
```

> 🔎 `npm install prisma` **sans** le `@7` installe une *release candidate* de
> la version 8, incompatible avec Better Auth. Et `@types/node@^20`, que pose
> le template, empêche purement et simplement l'installation de Vitest.

### Règles d'architecture

1. **Toute mutation passe par une Server Action.** Aucune Route Handler pour vos propres formulaires.
   *(Une exception admise : l'upload de photos, si votre solution le justifie.)*
2. **Chaque Server Action commence par** : vérification d'authentification → vérification d'autorisation → validation Zod. Dans cet ordre.
3. **Les composants sont serveur par défaut.** Chaque `"use client"` doit être justifiable en une phrase.
4. **Aucun état applicatif en mémoire** (pas de `let cache = []` au niveau module).
5. **Aucun identifiant écrit en dur, nulle part** — y compris dans
   `docker-compose.yml`, qui doit lire ses variables depuis `.env`. Un
   `.env.example` **réellement commité** documente ce qui est attendu —
   attention, le `.gitignore` de `create-next-app` contient `.env*`, qui
   l'exclut aussi ; il faut ajouter `!.env.example`. Vérifiez avec
   `git check-ignore -v .env.example`.
   Sachez **distinguer configuration et secret** (§ 6 du cours) : `DATABASE_URL`
   est de la configuration, `BETTER_AUTH_SECRET` est un secret.

## Étapes

### Étape 1 — Infrastructure et modèle

- [ ] `docker-compose.yml` avec PostgreSQL, démarrable par `docker compose up -d`
- [ ] **Aucun identifiant en clair dans `docker-compose.yml`** : il interpole
      `${POSTGRES_*}` depuis `.env`. Utilisez la forme `${VAR:?message}` pour
      que la commande échoue si une variable manque, plutôt que de démarrer un
      conteneur à moitié configuré.
- [ ] Schéma Prisma : `User`, `Annonce`, `Photo`, `Question`, `Favori` (+ les tables de Better Auth)
- [ ] Champ `role` sur `User` (`USER` / `AGENT` / `ADMIN`)
- [ ] **Au moins un `@@index` justifié** par une requête réelle de votre application
- [ ] Migrations versionnées dans le dépôt
- [ ] Script de *seed* : au minimum **2 agents distincts**, quelques `USER`, et des annonces réparties entre les deux agents
- [ ] Les comptes du seed sont créés **via l'API Better Auth**
      (`auth.api.signUpEmail`), puis leur rôle est attribué côté serveur

> 💡 Les **deux agents distincts** ne sont pas décoratifs : sans eux, vous ne pouvez pas tester l'autorisation (étape 4).

### Étape 2 — Lecture et rendu serveur

- [ ] `/annonces` : liste des annonces publiées
- [ ] `/annonces/[id]` : détail + questions/réponses
- [ ] **Paramètres de route correctement `await`és** (§ 4 du cours)
- [ ] Un `loading.tsx` ou un `<Suspense>` sur une partie lente, avec justification
- [ ] Pagination ou filtres sur la liste

### Étape 3 — Authentification

- [ ] Better Auth configuré (`emailAndPassword`), schéma généré puis migré :
      `npx @better-auth/cli generate` puis `npx prisma migrate dev`
- [ ] Le champ `role` déclaré en `additionalFields` avec **`input: false`**
- [ ] `/register`, `/login`, déconnexion
- [ ] Le rôle et le nom sont visibles dans la barre de navigation

> ⚠️ **`generate` réécrit `prisma/schema.prisma`.** Sauvegardez-le avant si vous
> y avez déjà mis vos modèles métier, et **relisez le résultat** : la fusion
> laisse parfois des champs en double.

> 🎯 **Ne hachez pas les mots de passe vous-mêmes.** Better Auth le fait
> (scrypt) et stocke le résultat dans la table `account`. Si vous créez un
> utilisateur par `prisma.user.create`, il n'aura aucun identifiant et ne
> pourra pas se connecter — c'est le piège classique du script de seed.

> 🎯 **`input: false` n'est pas un détail.** Il rend le rôle **inattribuable par
> le client** : un `curl` qui poste `role=ADMIN` à l'inscription obtient un
> compte `USER`. Vérifiez-le, c'est demandé dans les critères.

### Étape 4 — Autorisation (l'étape qui compte)

- [ ] CRUD complet des annonces via Server Actions
- [ ] **Un agent ne peut modifier ou supprimer que ses propres annonces**
- [ ] Un `ADMIN` peut tout faire
- [ ] Un `USER` ne peut ni créer ni modifier d'annonce
- [ ] Les annonces en brouillon ne sont visibles que de leur auteur (et des admins)
- [ ] Les questions sont réservées aux utilisateurs connectés ; les réponses, à l'agent propriétaire

**Test obligatoire** : connectez-vous en agent A, récupérez l'`id` d'une annonce de l'agent B, et tentez de la supprimer. **Si ça fonctionne, vous avez une faille IDOR.**

### Étape 5 — Validation et robustesse

- [ ] Schémas Zod pour toutes les entrées (formulaires, paramètres d'URL)
- [ ] Erreurs de validation affichées **champ par champ**, pas un message global
- [ ] Les valeurs saisies sont conservées après une erreur
- [ ] Un `id` inexistant ou non numérique produit un **404 propre**, pas une erreur serveur

### Étape 6 — Interface

- [ ] Navigation cohérente, design responsive
- [ ] Formulaires accessibles : `<label>` associés, messages d'erreur reliés aux champs
- [ ] Upload de photos (multiple ou glisser-déposer)
- [ ] États vides traités (« aucune annonce »)

### Étape 7 — Tests

- [ ] **Une base de données de test séparée.** Vos tests font table rase ; sans
      base dédiée, `npm test` efface vos données de développement et votre seed
      disparaît sans un mot. Prévoyez un `DATABASE_URL_TEST` et un fichier de
      setup qui bascule dessus.

Au minimum, avec Vitest :

- [ ] **Règles métier** : un agent ne modifie que ses annonces ; un `USER` ne crée rien
- [ ] **Validation** : un prix négatif, un titre trop court sont rejetés
- [ ] **Requêtes** : un brouillon n'apparaît pas dans la liste publique
- [ ] **Un test qui prouve l'absence d'IDOR** sur la suppression

Un test qui ne peut jamais échouer ne vaut rien. Vérifiez que chacun échoue quand vous cassez délibérément le code correspondant.

## Critères mesurables

Vérifiés automatiquement au rendu. Ils ne remplacent pas l'évaluation, ils la conditionnent.

| Critère | Cible | Comment le mesurer |
|---|---|---|
| `npm run build` | passe sans erreur ni warning TS | — |
| `npm run test` | tous les tests passent | — |
| **Invariance des requêtes SQL** sur `/annonces` | le nombre de requêtes est **le même** avec 3 annonces et avec 30 | logs Prisma (`log: ["query"]`), en comptant |
| **Budget de requêtes** sur `/annonces` | **≤ 2 + une par relation incluse** | idem |
| **Rendu serveur effectif** | le HTML brut contient déjà les annonces | `curl -s localhost:3000/annonces \| grep <un titre>` |
| **Codes de statut** | voir tableau ci-dessous | `curl -o /dev/null -w '%{http_code}'` |
| **Rôle non falsifiable** | une inscription qui poste `role=ADMIN` crée un compte `USER` | `curl` sur `/api/auth/sign-up/email` puis vérification en base |
| **Tests isolés** | `npm test` ne touche pas la base de dev | compter les lignes avant / après |
| **Pas d'identifiant en dur** | `grep -rE 'POSTGRES_PASSWORD:\s*\w' docker-compose.yml` ne renvoie rien | — |
| Démarrage à froid | `docker compose up -d`, migrate, seed, `npm run dev` | machine vierge |

### Le critère qui compte : l'invariance, pas un nombre

Un N+1 ne se définit pas par « beaucoup de requêtes » mais par **un nombre de requêtes qui croît avec le nombre de lignes**. Prisma résout chaque `include` par une seule requête groupée (`WHERE ... IN (...)`), donc une liste correcte émet `2 + nombre de relations incluses` requêtes — **quel que soit le nombre d'annonces affichées**.

Mesurez donc **deux fois**, avec peu puis beaucoup de lignes, et comparez. Si le compte bouge, vous avez un N+1.

### Codes de statut attendus

| Scénario | Attendu |
|---|---|
| agent propriétaire sur `/annonces/<id>/edit` | `200` |
| **agent NON propriétaire sur `/annonces/<id>/edit`** | **`404`** |
| visiteur anonyme sur `/annonces/<id>/edit` | `307` vers `/login` |
| `/annonces/999999` | `404` |
| `/annonces/abc` | `404` |

> ⚠️ **Piège de mesure, et il est vicieux.** Un code de statut n'est fiable que sur une route **non streamée**. Si un `loading.tsx` se trouve dans un dossier ancêtre, il met tout le sous-arbre en streaming : les en-têtes HTTP partent alors *avant* l'exécution de votre composant, et ni `notFound()` ni `redirect()` ne peuvent plus changer le statut — **tout répond `200`**, alors que votre code est correct.
>
> Si vous mesurez `200` là où vous attendez `404`, vérifiez d'abord vos `loading.tsx` avant de conclure à une faille. Et inversement : un `200` ne prouve pas l'absence de protection.

> 💡 **Ce qui n'est PAS un bon critère : le poids du JS.** On pourrait croire qu'un seuil de kilo-octets attrape les `"use client"` posés trop haut. Mesurez : une page à *zéro* composant client sert exactement le même JavaScript qu'une page qui en contient (socle React/Next commun, chunks identiques). À l'échelle de ce TP, le poids total ne discrimine rien. La discipline serveur/client s'évalue **structurellement** : combien de `"use client"`, où, et pourquoi.

L'usage d'assistants IA est autorisé et **attendu**. Ce qui est évalué, c'est votre jugement. Une page suffit :

1. **Ce que vous avez délégué**, et ce que vous avez écrit vous-mêmes — avec la raison du partage.
2. **Deux suggestions que vous avez rejetées**, avec la justification technique. *(Si vous n'avez jamais rien rejeté, soit vous n'avez pas assez utilisé l'outil, soit vous ne l'avez pas assez relu.)*
3. **Un bug introduit par génération** : lequel, comment vous l'avez détecté, comment vous l'avez corrigé.

Un `AI.md` vide ou complaisant est pénalisé. Un `AI.md` lucide est valorisé — y compris s'il raconte un échec.

### Déroulement de l'oral

Pas de présentation préparée. **Machine ouverte, sur votre dépôt.** Quelques questions, et on navigue dans votre code. Les deux membres du binôme doivent pouvoir répondre sur l'ensemble.

> ⚠️ L'oral ayant lieu **le lendemain du rendu**, c'est l'état du dépôt au 18 octobre 23h59 qui est évalué. Prévoyez que votre projet doit démarrer sur une machine vierge (`docker compose up -d && npm run dev`) : si ça ne démarre pas chez moi, on passe l'oral sur un projet qui ne tourne pas.

Exemples de questions — elles ne sont pas piégeuses, elles sont exactement ce que le TP enseigne :

- « Montrez-moi où est vérifié qu'un agent est bien propriétaire de l'annonce qu'il supprime. »
- « Combien de requêtes SQL pour afficher cette page ? Ouvrez les logs. »
- « Pourquoi ce composant est-il client et pas serveur ? »
- « Qui peut appeler cette Server Action ? »
- « Que se passe-t-il si j'envoie un prix négatif ? Montrez-moi. »
- « Vos sessions sont-elles en base ou dans un JWT ? Pourquoi ce choix, et qu'est-ce que ça change si je veux bannir un compte immédiatement ? »
- « Qu'est-ce qui casse si je supprime cette colonne en base ? »
